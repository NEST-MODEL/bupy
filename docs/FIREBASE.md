# Firebase: модель данных и безопасность

## Структура Firestore

```
users/{uid}                                   профиль владельца
users/{uid}/pets/{petId}                      питомец
users/{uid}/pets/{petId}/vaccinations/{id}
users/{uid}/pets/{petId}/medicalRecords/{id}
users/{uid}/pets/{petId}/tests/{id}
users/{uid}/pets/{petId}/medications/{id}
users/{uid}/pets/{petId}/medicationLogs/{id}
users/{uid}/pets/{petId}/events/{id}
users/{uid}/pets/{petId}/documents/{id}
```

**Отличие от исходного ТЗ:** питомцы лежат под `users/{uid}/pets`, а не в корневой `pets/{petId}`.
Так владение проверяется одним условием по пути (`request.auth.uid == uid`), без дополнительных `get()` внутри правил
(они считаются как чтения и увеличивают расход квоты). Если позже понадобится делиться питомцем с другим человеком — придётся добавить корневую коллекцию с участниками.

## Security Rules (`firebase/firestore.rules`)

- Всё запрещено по умолчанию.
- Доступ к `users/{uid}/**` только у `request.auth.uid == uid`.
- Профиль: разрешены только известные поля, `email` должен совпадать с email в токене, `createdAt` нельзя менять.
- Питомец: `species ∈ {dog, cat}`, имя 1–60 символов, ограничения на длину и типы полей, неизвестные поля запрещены.
- Записи питомца: только из списка коллекций выше, не более 40 полей в документе.

Ограничения, о которых стоит знать:
- Правила не удаляют подколлекции. При удалении питомца клиент должен сам удалить вложенные записи (будет в этапе 3).
- Валидация в правилах — защита от неверных данных и чужого доступа, но не замена проверкам в интерфейсе.

## Аутентификация

Email/Password (бесплатно на Spark). Сессия хранится SDK и переживает перезапуск. Сброс пароля — стандартное письмо Firebase.
Ответ на сброс пароля не раскрывает, существует ли аккаунт.

## Офлайн

Firestore инициализирован с `persistentLocalCache` (несколько вкладок): загруженные данные доступны без сети, записи синхронизируются при восстановлении соединения.
